## 1. 物理層

本体と プローブの UART は別チャネル。両端とも MAX3232 でレベル変換を行い、ケーブル区間は RS-232 ±12V level で伝送する。両端 MCU の UART ピン〜各基板 MAX3232 手前までは TTL 3.3V。

### 1.1 UART パラメータ

| 項目 | 本体 (IM-110T 本体基板) | プローブ (IM-110T プローブ基板) |
|---|---|---|
| MCU ペリフェラル | **LPUART1** | **USART2** |
| MCU ピン (TX / RX) | PC1 / PC0 (U4.9 / U4.8) | PA2 / PA3 (IC20.9 / IC20.10) |
| レベル変換 IC | MAX3232CPWR (U16) | MAX3232CPWR (IC21) |
| ボーレート | **38400 bps** (0.6.5 で 9600 から変更) | **38400 bps** (0.6.5 で 9600 から変更) |
| データ長 | 8 bit | 8 bit |
| パリティ | なし | なし |
| ストップビット | 1 bit | 1 bit |
| フロー制御 | なし (`UART_HWCONTROL_NONE`) | なし (`UART_HWCONTROL_NONE`) |
| オーバーサンプリング | (LPUART は 16x 固定) | 16x (`UART_OVERSAMPLING_16`) |

根拠:
- 本体: `../IM-110/Core/Src/main.c` 内 `LPUART1_Init` (`hlpuart1.Init.BaudRate = 38400` 等)
- プローブ: `../IM-110_Probe/Core/Src/main.c` 内 `USART2_Init` (`huart2.Init.BaudRate = 38400` 等)
- 38400 の妥当性 (0.6.5): 両 MCU とも sysclk 4MHz、16x オーバーサンプリングで BRR=104 →
  実ボー 38461bps (誤差 +0.16%、9600 時と同等)。発振器精度 (MSI/HSI16 各 ±1%) が支配項だが
  ボーレート非依存で 9600 の実績がそのまま担保。MAX3232 は 120kbps 以上保証で余裕。
- **FUP ブリッジ (§3.2.5) と CN2 デバッグ UART (USART1) は 9600 のまま**。FUP は STM32 ブート
  ローダーがオートボーのため PC 側ツール (stm32flash 等、9600 8E1) を変更しない。
- 本体 `PA11_CTS` / `PA12_RTS` は **外部デバッグコネクタ CN2 (CON6) に引き出されており、プローブ通信には使用していない** (`NET: PA11_CTS U4.44/R16/CN2.3`, `PA12_RTS U4.45/R15/CN2.2`)。

### 1.2 信号経路 / 物理コネクタ

```
[本体側 IM-110T 本体基板]                        [プローブ側 IM-110T プローブ基板]

  STM32L452 LPUART1                                STM32G070 USART2
  PC1=TX (U4.9)  PC0=RX (U4.8)                     PA2=TX (IC20.9)  PA3=RX (IC20.10)
     │   │   (TTL 3.3V)                               │   │   (TTL 3.3V)
     ▼   ▼                                            ▼   ▼
    MAX3232CPWR (U16)                                MAX3232CPWR (IC21)
     │   │   (RS-232 ±12V)                            │   │   (RS-232 ±12V)
     ▼   ▼                                            ▼   ▼
  CN4 (SM05B-SHLS-TF 5pin)  ── 4芯 RS-232 ケーブル ── 基板パッド直結 (半田固定)
  1: +5V        ────────────────────────────────────  TP25 VIN
  2: GND        ────────────────────────────────────  GND パッド
  3: PROBE_RXD  ─── (本体受信 ⇔ プローブ送信) ────────  TP28 TX (IC21.14)
  4: PROBE_TXD  ─── (本体送信 ⇔ プローブ受信) ────────  TP27 RX (IC21.13)
  5: GND        ────────────────────────────────────  GND パッド（予備）
```

- **本体側コネクタ**: CN4 (SM05B-SHLS-TF, JST SH シリーズ 5pin)。基板上の独立コネクタ。
- **プローブ側コネクタ**: **専用コネクタ無し**。回路図 (`回路図_IM-110T_プローブ基板_20260310.pdf`) の注釈「※相手のRx/Txと接続」で明示される通り、ケーブル芯線を TP25 / GND パッド / TP27 / TP28 に直接半田付けする固定構造。したがって **ケーブル単独での交換は不可**、ケーブル交換はプローブ基板ごと交換または再半田付けになる。
- **結線方向**: 本体 PROBE_RXD (= 本体が受信) ⇔ プローブ TX、本体 PROBE_TXD (= 本体が送信) ⇔ プローブ RX。クロス接続を守ること。
- **電源線**: 本体側 CN4.1 (+5V) からプローブへ給電、プローブ側 Q1 (RQ5A030AP, P-MOSFET) で逆接保護後に `+05P` レールへ。プローブ側にバッテリーは無いのでケーブル抜去 = プローブ電源断。

## 2. フレーム構造

本プロトコルは **ASCII テキスト・行指向**。バイナリフレーム (STX/LEN/CRC/ETX 等) や固定長ヘッダは一切無い。

### 2.1 基本形

```
<CMD>[,<param1>[,<param2>[...]]]<CRLF>
```

- `<CMD>`: 2〜4 文字の ASCII コマンド略号（§3 参照）。大文字小文字は区別する（実装は大文字前提）。
- `<param>`: カンマ区切りで 0 個以上。整数 / 浮動小数 / 固定長ビット文字列のいずれか（コマンドにより異なる、§3 参照）。
- `<CRLF>`: `\r\n` (0x0D 0x0A)。送信側は常にこの 2 バイトを付ける。

### 2.2 行終端の取り扱い

- **送信側**: 常に `\r\n` を付与する。プローブ応答 (`IM_110.c:392` 他)・本体送信 (`LinkSerial.c:744` 他) ともに確認済み。
- **受信側**: **LF (`0x0A`) のみで行終端と判定**。CR (`0x0D`) は単なるデータバイトとして受信バッファに積まれるが、行解析時は無視される。
  - プローブ: `IM_110.c:672` `if (RxData == LF) { end = 1; }`
  - 本体: `IM_110.c:195` `if (rx == LF) { Probe_uart_end = 1; }`
- **結論**: LF のみ送る実装とも相互運用可能だが、**両側 FW は CRLF で揃えているのでこれを正とする**。外部ツール/テスト治具もこれに従うこと。

### 2.3 パラメータ区切り

- 区切り文字は **カンマ `,`**。
- **送信側**はカンマのみで密に詰める (`"SADC,0011\r\n"` 等)。
- **本体側の受信パーサはスペース混入も許容**（`IM_110.c:284` `while (*ptr == ',' || *ptr == ' ') ptr++;`）。プローブ応答が `"%f, %f, ..."` (カンマ + スペース) を含むのはこの緩和に合わせたもの。
- **送信時にスペースを入れることは仕様外**。新規コマンド/応答を設計する際はスペース無しで送ること（将来的な厳格化の余地を残すため）。

### 2.4 文字コードと制限

| 項目 | 値 |
|---|---|
| 文字コード | ASCII (7-bit) のみ。非 ASCII バイトは仕様外 |
| 最大フレーム長 | 510 バイト（LF 含む。プローブ受信バッファ 512 バイト − 安全域 2）  |
| バッファオーバーフロー時 | プローブ側 `IM_110.c:678-681` で **強制的に位置 510 を LF に上書きして処理**（エラー応答は出ない）。Flash パラメータ一覧 (`RPP` 応答) は複数行 (各行独立) で 1 行あたり 512 未満に収まる設計 |
| フレームチェックサム | **無し**。パリティ・CRC ともに未使用 |

**バッファオーバーフロー発生条件の見積もり** (v0.4.0 で確認・現状維持):

正常運用では発生しない。発生しうるのは以下のような異常ケースのみ:

| ケース | 発生可能性 |
|---|---|
| 本体 FW が `\r\n` 付与を忘れて長文を送る | FW バグ。開発中の検出対象 |
| 本体 `LinkSerial.c:259` の **BLE パススルー** (`Probe_SendSerialData(&RecvData[2])`) 経由で、BLE クライアントが LF 無しの 512+ バイトを送り込む | 実質皆無。BLE 通信は CPU 側 / BT モジュール側のアクション駆動で、自発的に大量データが流れる構造になっていない。ほぼ全ての判定処理でタイムアウト構造になっており、暴走状態にならない |
| 信号品質劣化で `\n` (0x0A) がビット化けし LF 判定されない | 極めて低確率。§5.3 の PE/FE/NE/ORE 検出が先に発火する想定 |

発生した場合も強制 LF 挿入により「長い偽コマンド」を 1 回処理 → 大抵 `NG\r\n` 応答で終わる副作用で済む。プローブは壊れず、次の行から通常処理に復帰する。

将来、発生頻度が判明して実害が出るなら以下のいずれかを検討（現時点では不要）:
- バッファ全破棄 + リセット（途中コマンドも失われるが状態がクリーン）
- `NG,OVERFLOW\r\n` の明示返送（A.10 の NG 理由コード化と連動）

### 2.5 応答パターン（種別）

応答はコマンドごとに以下のいずれか:

| 種別 | 形式 | 例 | 使用コマンド |
|---|---|---|---|
| `OK\r\n` | 単純成功 | `OK\r\n` | `SP`, `SEL`, `SS`, `MS`, `SID`, `SADZ`, `SADS`, `SADA`, `SADC` |
| `NG\r\n` | 単純失敗 | `NG\r\n` | 上記コマンドのパラメータ範囲外・未知コマンド（§5 参照） |
| 値応答 1 行 | コマンド固有の値文字列 + `\r\n` | `IM-110 Probe Ver.0.11\r\n` | `VR`, `MD` |
| 複数行応答 | 複数行のテキストを個別 `\r\n` で送信、末尾に `OK\r\n` or 固定文 | (§3.2 `RPP` 参照) | `RPP`, `WPP`, `RPI` |
| 自律送信 | `MS,1` ON 中、プローブから周期送信 | (§3.3 参照) | `MS` (MS_flag ON 時) |

### 2.6 エンディアン

ASCII テキスト前提のためエンディアン概念は適用されない（数値は 10 進文字列 or float 文字列で送受信）。

## 3. コマンド一覧

全コマンドは **本体 → プローブ方向** のみで発行される。プローブから本体への自律送信は §3.3 (MS) のみ。

**大文字小文字**: コマンド名は **大文字 (A-Z) のみ** 有効。小文字・大小文字混在 (`vr`, `Vr`, `mS` 等) はすべて `NG\r\n` 返送される (プローブ実装が `strncmp` で大文字比較するため)。ユーザー入力 / 治具からコマンドを送る際も大文字で統一すること。

### 3.2 応答詳細（値応答・複数行応答）

#### 3.2.1 `VR` — 製品名・バージョン

```
→ VR\r\n
← IM-110 Probe Ver.0.11\r\n
```

- 定義: `IM-110_Probe/Core/Inc/IM_110.h` `#define P_NAME "IM-110 Probe"`, `#define P_VER 11`
- 書式: `"%s Ver.%d.%02d\r\n" → name, ver/100, ver%100` (`IM_110.c:392`)

#### 3.2.2 `MD` — 測定値 1 回送信（および MS 自律送信の中身）

```
→ MD\r\n
← <mV[0]>, <mV[1]>, <mV[2]>, <mV[3]>, <mV[4]>, <pressure hPa>\r\n
```

- 6 個の `float` をカンマ + スペースで区切り（`"%f, %f, %f, %f, %f, %f\r\n"`、プローブ `IM_110.c:405`）
- 内部配列 `AD_AVE_mV[5]` (float) + 気圧センサ値 1 個
- 移動平均は `SADA` で設定した回数で計算済み（0.6.6 から既定 0 = 瞬時値。平均は本体側で実施）
- pressure hPa: HSPPAD143A 気圧センサー (I2C2 / PA11=SCL, PA12=SDA) の実測値。**現行リビジョンでは実装済み・稼働中**で、`HSPPAD143_ReadPressure()` が周期取得した hPa を返す。**`MD` 応答書式は固定** — 6 番目の float に実測 hPa が入る。
- HSPPAD143A 内蔵の**温度センサ値は `MD` 応答には採用しない** 方針（本水質計測装置の用途上必要な情報は気圧のみ）。将来温度計測が必要になった場合は `MD` 書式を拡張せず、新コマンド（例: `MDT` = Measure Data with Temperature）を別途追加する

**`AD_AVE_mV[0..4]` の各要素が指すもの**:

`AD_AVE_mV` の index は MCP3424 の物理 ch と 1 対 1 ではなく、**`SEL3` (`SS` コマンド) の状態でインデックスが動的に変わる** ため注意が必要:

| 配列 index | 対応する物理計測 | 更新条件 | 用途の想定 |
|---|---|---|---|
| `AD_AVE_mV[0]` | MCP3424 CH1 | `SADC` bit 0 = 1 | — |
| `AD_AVE_mV[1]` | MCP3424 CH2 | `SADC` bit 1 = 1 | — |
| `AD_AVE_mV[2]` | MCP3424 CH3 の **SEL3 = LOW** 時 | `SADC` bit 2 = 1 **かつ** `SS,0` | 通常ゲイン x1 測定 |
| `AD_AVE_mV[3]` | MCP3424 CH4 | `SADC` bit 3 = 1 | — |
| `AD_AVE_mV[4]` | MCP3424 CH3 の **SEL3 = HIGH** 時 | `SADC` bit 2 = 1 **かつ** `SS,1` | 同一 ch3 を PGA gain x2 で再測定 (`IM_110.c:196-201`) |

要点:
- **`SADC` は 4 bit (ch0-ch3) の制御のみ**。`AD_AVE_mV[4]` は SADC で直接有効/無効化できず、「ch2 が有効 + SEL3 HIGH」の組み合わせで自動的に更新される
- `SS,0` と `SS,1` を切り替えると、**同じ物理 ch3 の読み取り値が `[2]` と `[4]` のどちらに流れるかが切り替わる**。更新されなかった側は古い値が残留

**無効化 ch / 未更新 ch の値**:

`AD_AVE_mV[]` はゼロ初期化 (C 標準、グローバル) される。一度も有効化されていない ch は `0.000000`。一度有効化されたが後で無効化された ch は **直前の値が残留** (クリア処理なし)。本体側は必要に応じて `SADC` / `SS` 設定を自身で保持し、有効な index だけを読む責任がある。

**具体例**:
```
起動直後 SADC=0000:        0.000000, 0.000000, 0.000000, 0.000000, 0.000000, 0.00
SADC,0011 (ch0+ch1 有効):  1.234,    -0.567,   0.000000, 0.000000, 0.000000, 0.00
SADC,1111 + SS,0:          1.234,    -0.567,   2.100,    3.456,    0.000000, 0.00
SADC,1111 + SS,1:          1.234,    -0.567,   2.100,    3.456,    5.678,    0.00  (※[2]は据え置き、[4]が更新)
SADC,0000 に戻す:          1.234,    -0.567,   2.100,    3.456,    5.678,    0.00  (全て残留)
```

#### 3.2.5 `FUP` — ファーム更新モード移行（リペア/製造用）

プローブを **STM32 ROM システムブートローダー**へ移行させ、UART (USART2) 経由でファーム書き換え可能な状態にする保守コマンド。**通常の測定フローでは使用しない**。プローブがケース内に接着固定され SWD (J4) が使えなくなる運用を想定した、ケーブル経由のファーム更新経路（方式A）の入口。

```
→ FUP,45063\r\n        (45063 = 0xB007 "BOOT" 固定ガード値)
← OK\r\n               (ガード一致時。直後にプローブはリセットし ROM ブートローダーへ移行)
← NG\r\n               (ガード値不一致・欠落時。状態は変化しない)
```

- **移行後**: プローブは ROM ブートローダーが USART2 (PA2/PA3) を占有し、**AN3155 プロトコル / 8bit・Even parity(8E1)・自動ボーレート** で書き換え待ちになる。以降アプリのコマンド応答は返らない。書き込みツールは STM32CubeProgrammer / stm32flash。
- **ガード値**: 誤爆防止のため固定値 `45063` を要求。不一致・省略は `NG`。ノイズで偶発移行しても、Flash を消去しなければ**電源再投入でアプリへ復帰**する（下記リセット要因ゲートにより、コールド起動では必ずアプリへ復帰）。
- **実装 (プローブ, Ver.0.13〜)**: `OK` 送信（ブロッキング, TC 完了）→ 移行要求マーカ格納 → `NVIC_SystemReset()`。リセット後 `main()` 冒頭（**IWDG 起動前**）でマーカを検出し、システムメモリ `0x1FFF0000` へジャンプ。IWDG（software mode, Reload 4095 ≒ 約2秒）が動いたまま移行すると bootloader が約2秒でリセットされ書込が破綻するため、必ず「マーカ＋リセット」で IWDG 未起動状態にしてから移行する。
- **移行要求マーカ = TAMP バックアップレジスタ (Ver.0.17〜, 重要 / UART沈黙対策)**: 当初 (Ver.0.13-0.16) はマーカを `.noinit` SRAM 変数に置いていたが、`.noinit` はコールド起動 (POR/BOR/ピン/IWDG リセット) で**不定値**になり、電源投入時に偶発的にセンチネルと一致してブートローダーへ落ち、アプリが起動せず USART2 が沈黙する不具合があった（起動時 `RPG`（当時は接続時読出コマンド）に無応答→本体 3 秒タイムアウト、実機確認）。**Ver.0.17 でマーカを TAMP バックアップレジスタ (`TAMP->BKP0R`) に変更し `.noinit` を全廃**。バックアップレジスタは **POR (電源再投入) で必ず 0 クリア**され、**`NVIC_SystemReset()` は跨いで保持**されるため、コールド起動での誤爆が原理的に起きない。加えて `main()` 冒頭のジャンプ判定は **「直前がソフトリセット (`RCC_FLAG_SFTRST`)」かつ マーカ一致** の AND 条件とし、それ以外 (コールド起動含む) は要求を破棄。判定前後で毎回 `__HAL_RCC_CLEAR_RESET_FLAGS()` によりリセットフラグを浄化する。正規の FUP 経路は `NVIC_SystemReset()`=ソフトリセットなので `SFTRST` が立ち、正しく移行する。バックアップレジスタ書込には起動時に PWR DBP (`HAL_PWR_EnableBkUpAccess`) と RTCAPB クロック (`__HAL_RCC_RTCAPB_CLK_ENABLE`) を有効化する。
- **復旧 (アンブリック)**: 書き換えはベクタ先頭ページ消去から始めること。途中失敗で Flash 先頭が空なら、次回電源投入時に ROM ブートローダーの empty check が働き BOOT0 無しで自動的に書換待ちに入る（要 RM0454/AN2606 実機確認）。
- **本体 (マスター) 側ブリッジ = 実装済み（通常 FW の追加機能）**: 別ビルドではなく、本体が USART1(PC/CN2) で **`FUP,45063`** を受信すると `CheckSerialCMD()` から `ProbeFupBridge_Run()` を起動する（`IM-110/Core/Src/LinkSerial.c` / `main.c`）。動作: (1) プローブへ `FUP,45063`(LPUART1, 9600 8N1) を発行しブートローダーへ移行、(2) 実行中アプリの DMA 受信を停止、(3) USART1・LPUART1 を **115200 8E1** へ再設定、(4) `PC(USART1) ↔ プローブ(LPUART1)` をポーリングで透過中継（ORE/PE はクリアしロック回避）。**復帰しない（終了＝電源OFF）**。本体応答は移行直前に `P:FUP\n`。
  - **PC 側手順**: USART1 アプリ時は 115200 8N1。`FUP,45063` を 115200 8N1 で送る → `P:FUP` 受信 → 本体が 8E1 に切替わる（ボーレートは 115200 のまま、パリティのみ even へ）→ PC も **115200 8E1** にして `stm32flash` / STM32CubeProgrammer でプローブを書換。完了後は本体・プローブとも電源再投入で通常動作へ復帰。
  - 旧方式（`make FUP_BRIDGE=1` のコンパイルフラグ切出し）は廃止し、ランタイム機能へ一本化した。

#### 3.2.6 `RPG` / `WPG` / `WSC` — 統合ストア 32B ページ転送（校正係数・パラメータ）

> **改訂（2026-07-23, プローブ Ver.0.19 予定）**: 旧 `RCF`/`WCF`/`WCS`/`WCFC`（＋ver2 `WCM`/`WCK`/`WCZ`/`WCT`）の **per-eq/per-mode 意味論プロトコルを廃止**し、**32B ページ単位のバイト転送**に一本化する。理由は `mlss-calc-reference.md §12/§A-2` が確定した **「1 機能 = 32B ページ／プローブ flash ⇄ 本体 EEPROM ミラーをページオフセット完全同一（バイト一致）」** 契約に、旧プロトコルが未追従だったため。旧 `cf[7]`/`kiza` は旧測定モデルの係数枠であり、現行の再設計モデル（`§8`, 1700 span・2 次式×k_No・TR 累乗・kiza 廃止）とも非互換。**本コマンド群がプローブ⇔本体の係数・パラメータ転送の唯一の真実源**。旧コマンドは受理しない。

**目的**: プローブ性能に関わる**全係数・調整パラメータ**を**プローブ側 flash を真実源**として保持し、本体側 EEPROM は**バイト完全同一のミラー**（非権威キャッシュ）とする。本体基板のみ交換・プローブ付け替えのいずれでも測定値が正しく出る（§A-2 3 層モデル）。濃度換算は本体で実行し、係数はプローブが保管する。

**転送単位 = 統合ストア `probe_store_t` の 1 ページ（32B）**。

- ストア実体 = **25 ページ × 32B = 800B**（`probe_store.h`、`mlss-calc-reference.md §12`）。ページ番号 `N` = `0..24`、各ページの意味は §12 で固定（Page0=ヘッダ、Page1-3=共通調整/設定、Page4-16=係数/SetVal、Page17-19=出荷時3点調整 捕捉点、Page20-22=現場スパン校正 捕捉点、Page23-24=温度補正 捕捉点）。
  - 履歴: 2026-07-31 に 16→17 ページ（LED_Out ページ分離）、2026-08-02 に 17→23 ページ（出荷時3点調整 Page17-19 と現場スパン校正 Page20-22 の捕捉点永続化）→ 同日 23→25 ページ（温度補正捕捉点 Page23-24、v0.6.1）。本節の旧記述（16 ページ）は 07-31 改訂が未反映だった。
  - **旧レイアウト（23 ページ=736B・20 ページ=640B 中間版・17 ページ=544B）イメージは読出時に自動移行**する（両側 `store_upgrade_legacy()`: 先頭 n ページの magic/XOR/checksum が旧定義で有効なら、残りページを 0（=捕捉点なし）で追加して再封緘）。17 ページ未満の旧々イメージは従来どおり無効＝新品扱い。
  - **バージョン組合せ制約**: 25 ページ化した本体 (Ver.0.27〜) と旧ページ数のプローブを混在させた場合、本体は旧ページ数の `RPG` も受理して移行するが、`WPG` の新ページはプローブに拒否され完全同期できない。**両側同時リリース必須**（§3.3）。
- **本体 EEPROM ミラーは同一 25 ページを連続配置**し、**相対レコード N == プローブ page N（バイト完全一致, §A-2）**。ページ内バイト割付・float 表現（IEEE754 single, リトルエンディアン）・末尾 XOR 位置まで両側同一。ミラー位置は 2026-08-02 に EEPROM page61 → **page19**（撤去済み legacy 校正領域の再割当、現行 page19-43）へ移設。旧位置は移行読出しのみ。
- ページ整合性: 各 32B の `[31]` = `[0..30]` の XOR（`probe_store.h store_page_xor`、本体 EEPROM `Eeprom.h:10` と同一機構）。ストア全体は Page0 の `checksum(4B)`（`store_calc_checksum`）で担保。
- **ワイヤ表現**: 1 ページ = **64 hex 文字**（32B をアドレス昇順に `%02X`、`store` 構造体そのままの生バイト列）。**per-field の float テキスト化はしない**（意味は共有 struct が担保、往復誤差ゼロ）。

##### 読み出し `RPG`（本体 ← プローブ、接続時に 1 回）

```
→ RPG\r\n                              (全 25 ページ一括ダンプ)
← PGV,<magic8hex>\r\n                  (ストア有効。例: PGV,494D3253  = 'IM2S')
← PG,0,<64hex>\r\n                     (Page0 ヘッダ 32B)
← PG,1,<64hex>\r\n
←  …(Page2..23)…
← PG,24,<64hex>\r\n                    (Page24 SS 温度補正捕捉点)
← OK\r\n

→ RPG,<N>\r\n                          (単一ページ。N=0..24)
← PG,<N>,<64hex>\r\n
← OK\r\n                               (N 範囲外は NG のみ)
```

- 行数（一括）: `PGV` 1 + `PG` 25 + `OK` 1 = **27 行**。伝送量 ≈ 25×70B ≈ 1.8KB。
- **ストア無効時**（magic 不一致・checksum NG・いずれかのページ XOR NG）は `NG\r\n` のみを返す。本体はミラーへフォールバックする（§A-2 バックアップからの復旧経路）。
- **flash 未書込（全 0xFF = 新品/消去済み）の場合はプローブが起動時に自ら §12 既定で新品化して flash 確定**するため（Ver.0.20〜, 2026-08-02）、`RPG` は常に有効ストアを返す。`NG` が返るのは書込中電源断等の**破損**時のみ。破損はプローブ側で上書きせず、本体ミラーの正しい係数を潰さない。
- 先頭文字が `P`（大文字）= 応答行のため、測定値行（`0-9`/`-` 始まり、§3.4）と排他。`RPG` は **MS 停止中**に実行すること。
- **ホスト実装注記（2026-08-06、本体 Ver.0.41 実測に基づく）**:
  - **コマンド間ギャップ**: プローブは応答送信後に受信バッファの後始末を行うため、応答受信から
    **20ms 以上**空けて次コマンドを送ること。応答直後に被せるとコマンド先頭が取り損なわれ、
    不完全コマンド扱いの `NG` が返る（起動時 `RPG` が NG になり BOOT:2 となっていた実測真因①）。
  - **一括応答はバルク受信推奨**: 27 行 ≈1.8KB は 38400bps で無間隙に届く。受信中に行の切り出し・
    バッファ操作（特に割込禁止を伴うもの）を行うと低クロックのホストでは取りこぼす
    （本体 4MHz で実測、真因②）。受信完了（末尾 `OK\r\n`/`NG\r\n`）までバッファへ蓄積のみ行い、
    完了後にパースすること（本体実装 = `Probe_BulkCmd`）。

##### 書き込み `WPG` / 確定 `WSC`（本体 → プローブ、校正確定時・マイグレーション時）

プローブは起動時に flash ストアを RAM 像（`g_store`）へ読み込む。`WPG` は RAM 像の該当**ページのみ**更新し、`WSC` で RAM 像全体を封緘（magic/ver/checksum/全ページ XOR）して flash へ確定する。校正時は変更したページだけ送れば良い（未変更ページは保持される）。

```
→ WPG,<N>,<64hex>\r\n   ← OK / NG   (RAM 像の page N を更新。N 範囲外／長さ≠64／hex 不正／page XOR 不一致 は NG)
→ WSC\r\n               ← OK / NG   (commit: store_seal 付与し STORE_AD へ 800B 書込。§12 全 25 ページ一括消去→書込)
```

- **`WPG` はページ末尾 XOR を検証**してから RAM 像へ格納する（`store_page_xor` 不一致＝転送破損として NG）。本体は送出前に自ミラーで XOR を封緘しておく。
- **マイグレーション**（新品プローブ／既存校正機）: 本体が変更ページ（or 全 16 ページ）を `WPG` で送ってから `WSC` する。ID／最終更新日は Page0（`store_hdr_t`）に含めて送る。
- `WSC` 前に電源断しても flash は前の内容のまま（RAM 像のみ更新のため）。commit 成功で確定。
- **電源 OFF 一括書戻し（§A-2）**: 運用中の校正/調整は本体 RAM に反映し、制御シャットダウン窓で **プローブ（`WPG`×変更ページ＋`WSC`）と本体 EEPROM ミラーの両方**へ**同一 ID・同一最終更新日**で書く。flash-busy 窓を測定中にまたがないことで旧係数格納方式で見られた通信不安定を回避する。

| 6-10 | MLSS No.21-30 | 独立2次式×10（2式/頁） |

| 14 | TR ゼロ・ベース・校正 | TRZR(現場枠)/累乗a,b/SP_A,B,C/**TRZR_Ship(出荷時枠, offset24。2026-08-03 追加)**（温度=SS参照）。旧イメージは TRZR_Ship=0 → 読出側が TRZR で補完（移行） |
| 15 | TR No.21 | 校正後累乗a,b |
| 16 | SetVal | MLSS/SS/TR × (SetVal1,SetVal2) |
| 17 / 18 / 19 | MLSS / SS / TR 出荷時3点調整 調整係数 | 常設モデル: x[3]=各点の受光mV (ゼロ/スパン/中間。MLSS/SS の[0]は未使用=Page4/11 zr が真実源)、y[3]=設定値、valid=0x07固定。新品時から既定式と整合する初期値入り。ADBOAD 16-24 (2026-08-02 温度補正6画面挿入後の番号) の実行は該当係数のみ置換し常に3点で式を再計算（スパン実行は中間を ABS 1/2 へセットし直し=実質1次式、`adboad.md`） |
| 20 / 21 / 22 | MLSS / SS / TR 現場スパン校正 捕捉点 | x[0]=フル点 raw mV(ゼロ校正前), x[1]=中間点 raw mV, y[0..1]=校正時基準値, valid(bit0=フル/bit1=中間)。2点校正(ADCAL)=フル点を記録し**中間点を破棄して直線化**（従来機の「中間点を 1/2 で算出・セット」と同結果）。中間校正(MCAL)=保存済みフル点を使い**中間点の選択だけで即 3 点再計算**（フル点未捕捉なら演算エラー — 先に ADCAL 実施） |

- ストアの正当性は `magic` + 各ページ XOR + checksum で判定する。ページ構成を変える場合は両側同時更新のうえ、実機を `RPF`（新品化）してから再調整する（§3.1）。
- 相関式初期化・ゼロ初期化は Page4/11 の出荷時ベース・Page3/10 の ZR_出荷時 を対応枠へコピー（本体側処理、§12）。旧 `RCF` の `CM/CK/CZ/CT`（Mode_CF/機差補正/ADZR/温度）は本モデルでは Page3-15 の 2 次式・ゼロ・温度枠へ吸収（`kiza` は廃止, §8）。

#### 3.2.7 `MDR` / `RPF` — 調整・デバッグ用コマンド（プローブ Ver.0.18〜）

基板調整モード（ADBOAD, `adjust-mode-design.md`）のブリングアップ／デバッグを、本体側から全状態を観測しながら行うために追加した保守系コマンド。**通常の測定フローでは使用しない**。

##### `MDR` — 生 AD 値 mV（span 非依存）を 1 回取得

`MD`（§3.2.2）が返す `AD_AVE_mV[]` は **span 正規化済み**（`出力 = 生mV × ADC_SPAN_INI(1450) / ADC_Span`, `IM_110.c:200,206`）で、かつ移動平均後の値。LED PWM duty 調整では **正規化前・平均前の素の mV** を見たいので、それを直接返す。

```
→ MDR\r\n
← MDR,<raw0>,<raw1>,<raw2>,<raw3>,<raw4>\r\n
```

- 5 個の `float`（mV）。`AD_AVE_mV[]` と同じ index レイアウト（[0]MCP3424 CH1 / [1]CH2 / [2]CH3(SEL3 LOW) / [3]CH4 / [4]CH3(SEL3 HIGH, PGA x2)）。
- 値の出所は **その瞬間の生変換値** `(int16_t)MCP3424_AD_Digit[ch] × lsb (+ ADC_CH4_VREF for ch4)`, `lsb = 0.03125 (ch4) / 0.0625 (他)`。**`SADS` / `SADZ` が span/zero 基準として記録するのと同一のソース**なので、`MDR` で読める生 mV と `SADS,N` が `ADC_Span[N]` に latch する値は一致する。
- どの index が新鮮かは `MD` と同じく `SADC`（有効 ch）と `SS`（SEL3 で [2]/[4] 切替）の設定に従う。無効/未更新 ch は残留値または 0。
- **応答は英字 `M` 始まり** → §3.4 の行分類で「応答行」に分類され、測定値行（数字/`-` 始まり）と衝突しない。MS 自律送信 ON 中でも安全。
- 気圧 hPa は含めない（生 AD 観測が目的）。移動平均後の値・正規化後の値が必要なら従来どおり `MD` を使う。

##### `RPF` — プローブを新品（工場出荷前）状態へ全初期化

プローブ flash に記憶している**全パラメータ・全係数を新品状態へ戻す**。`RPI`（RAM 上で初期化するのみ・要 `WPP`）と異なり、**統合ストア（`probe_store_t` 512B）を §12 既定値で初期化 → flash（STORE_AD/Page63）へ確定まで 1 コマンドで実施**する。ADBOAD デバッグを「新品プローブ」から反復するための入口。

```
→ RPF\r\n
← OK\r\n     (統合ストアの既定値初期化＋flash 書込が成功)
← NG\r\n     (flash 操作が失敗)
```

- 実施内容:
  1. `Set_Param_INI()` — 統合ストアに無いレガシー live 変数を初期値へ（RAM）
  2. `store_new_probe_init()` — 統合ストアを §12 既定値（Product Name / Probe ID=`0xFFFFFFFF` / `ADC_Span`=1450 / `LED_Out`=`LED_OUT_INI` 0.36 / k_depth=1.0 / 係数=未校正0）で初期化し、封緘して STORE_AD（Page63, 512B）へ確定。既定値を live へも反映
  3. LED PWM duty を `LED_OUT_INI` で HW へ反映（`Set_PWM_Duty`）
  4. 以降 `RPG` はこの新品ストア（Page0=有効 magic）を返す。本体は ID 変化／未校正係数を検知して新品扱い（§A-2）
- **破壊的**：現場校正済みプローブに送ると **統合ストアの全係数（Page3-15）と全パラメータを既定値へ全消去**する。製造・ブリングアップ・デバッグ専用。誤爆が問題になるなら `FUP` 同様のガード値方式（`RPF,<magic>`）への変更を検討（現状は引数なし）。
- タイムアウト区分は **slow**（統合ストア 512B の 2KB ページ消去/書込を含む、§4.2）。
- flash 書込中の CPU ストールによる ORE は §5.3 の `HAL_UART_ErrorCallback`（プローブ Ver.0.17 実装済）で救済される。

### 3.3 自律送信（`MS` 有効時の周期送信）

> **【0.6.4 / 2026-08-04 方式変更】本体は MS 自律送信を使用しない（ポーリング方式へ一本化）。**
> 測定値取得は **本体主導のポーリング**: 本体が **500 ms 周期**で `MD\r\n` を送信し、1 行の応答
> (§3.2.2 と同一フォーマット) を受信する。要求応答型のため、本体側のコマンド送信前バッファクリアと
> 受信が競合しない。
> - **変更理由**: MS 自律ストリームと本体の受信バッファクリア（コマンド送信前掃除）が非同期に競合し、
>   受信途中の測定値行がクリアで先頭切断され、数字始まりの断片が測定行として誤パースされる事故が発生
>   （欠けたフィールドが `strtof("")=0` となり、水深ゼロ基準 `Depth_offset` に 0 がラッチされ
>   水深 6.00 m 振り切りとなる。2026-08-04 実機で確認）。ポーリングなら送受信の順序が構造的に保証される。
> - 本体は起動 FINALIZE で `MS,0` を送信（冪等な保険）し、以後 MS を有効化しない。
>   ランタイムの `MS,1` 送出コード（`Probe_ResumeMS`/`Probe_EnsureMS_On`）は本体 Ver.0.33 で撤去。
> - `MS` コマンド自体はプローブに残置（プローブ単体試験・レガシー用途）。以下の記述はその用途向け。
> - §3.4 の行分類・逐次保証はポーリング方式でも防御として引き続き有効。
> - §5.4 の切断判定は「MS 間隔監視」から「MD 応答の鮮度監視」に読み替える（タイムアウト値 2000 ms は不変）。

- トリガ:
  - **`MS,1\r\n`** (推奨、v0.4.0 以降): `MS_flag = 1` を明示セット。冪等なので重複送信しても ON のまま
  - **`MS,0\r\n`**: `MS_flag = 0` を明示セット。冪等な停止
  - **`MS\r\n`** (引数省略、レガシー): 受信毎に `MS_flag ^= 1` でトグル。プローブ単体試験用途で残置
- ON 時はプローブが **500 ms 周期** (`TIMER_UART_OUTPUT = 500`, `IM_110.h`) で §3.2.2 の `MD` 応答と同一フォーマットの測定値行を送信
  - **【2026-08-03 訂正】** 本欄は長らく実装値 1000 ms を逆抽出して記載していたが、設計意図・本体側実装の前提（`Probe_Request_MD` コメント「約0.5s間隔」、本体移動平均窓 10本×500ms=5秒、KI-3/KI-4 の見積もり）はすべて 500 ms。**500 ms を正とし、プローブ実装 (旧 1000) を訂正**（プローブ Ver.0.23）。1 行 ≈60 バイト ≈62 ms @9600bps のため帯域上も問題なし
- 実装: `main.c:149-154` (プローブ側、TIM1 1ms 割り込みでソフトタイマを進めて周期判定)
- 自律送信中にコマンド応答（`OK` など）が同じチャンネル上で混在する可能性があるが、本体パーサは §3.4 の行分類ルールで確実に区別できる。

### 3.4 応答行と測定値行の区別

MS 自律送信が ON の状態でコマンドを発行すると、測定値行と応答行が同じ UART ストリームに流れる。本体パーサは **受信した 1 行の先頭 1 文字** で用途を判別する。

**分類ルール**:

| 先頭 1 文字 | 用途 | 処理 |
|---|---|---|
| `0`–`9` または `-` | 測定値行（`MD` / 自律送信） | `strtof` で 6 個の float をパース、測定値として処理 |
| `A`–`Z`（大文字アルファベット） | コマンド応答 | 直前に送ったコマンドの応答として扱い、§3.2 の書式で解釈 |
| 空行 / `\r` 単独 / その他制御文字 | ノイズ | 無視 |

**網羅性の根拠**（プローブが実際に送る行の先頭文字一覧）:

| 行の種別 | 先頭文字 | 例 |
|---|---|---|
| `MD` / MS 自律送信の測定値 | `0`–`9` / `-` | `1.234, -0.567, 2.100, 0.000, 0.000, 0.000\r\n` |
| `MDR` 応答（生 mV、§3.2.7） | `M` | `MDR,1698.2,1650.1,2100.0,0.0,0.0\r\n` |
| `OK` 応答 | `O` | `OK\r\n` |
| `NG` 応答 | `N` | `NG\r\n` |
| `VR` 応答 / 起動バナー | `I` | `IM-110 Probe Ver.0.11\r\n` |
| `RPP` Product Name / Probe ID / RPI / WPP 成功 | `P` | `Product Name: IM-110\r\n`, `Probe ID: 1234567890\r\n`, `Parameters saved to flash.\r\n`, `Parameters reset to initial values.\r\n` |
| `RPG` 応答（統合ストア転送、§3.2.6） | `P` | `PGV,494D3253\r\n`, `PG,0,49...\r\n` |
| `RPP` ADC Zero/Span/Span_S | `A` | `ADC Zero[0]: 0.000000\r\n` |
| `RPP` LED Out | `L` | `LED Out[0]: 0.458000\r\n` |
| `WPP` 失敗 | `F` | `Failed to write parameters to flash.\r\n` |

→ 測定値行は必ず `0-9` または `-` で始まり、応答行は必ずアルファベットで始まる。**両者は先頭 1 文字で排他的に区別可能**。

**プローブ側の契約（逐次保証）**:
- プローブは 1 つのコマンドに対する応答を **完結させてから MS 自律送信を再開する**。単一応答の途中（例: `RPP` の複数行ダンプの途中）に測定値行が割り込むことは無い
- 現状実装: プローブ main loop は `CheckSerialCMD()` の処理と `uart_Put_Measure_Data()` (自律送信) を逐次で呼んでおり、それぞれのブロック内で送信を完結させるためインターリーブは発生しない (`main.c:137-154`)
- 本仕様はこの逐次性をプローブ側 FW の契約として固定する。将来プローブを RTOS 化する等して送信処理を並行化する場合、この契約を破らないよう送信のクリティカルセクションで排他制御すること

**本体パーサ状態**:
- 本体は応答待ちフラグ (`Probe_cmd_pending`, `IM_110.c:121`) を持つが、**測定値行の受信は応答待ちの有無にかかわらず常時受け付ける**
- 応答行が到着した場合は到着順で `cmd_pending` に対応付けてタイムアウトタイマー (§4.3) を止める
- 応答待ちフラグが立っていない状態で応答行が来た場合（通常発生しないが、起動時バナー等）はログのみ記録して破棄

## 4. タイミング

### 4.1 物理・HAL 層

| 項目 | 値 | 備考 |
|---|---|---|
| ボーレート | 9600 bps | 1 バイト ≒ 1.04 ms (10 bit frame) |
| 典型コマンド長 | 〜20 バイト | 1 行送信 ≒ 20 ms |
| `MD` 応答長 | 〜80 バイト (float 6 個) | 1 行送信 ≒ 80 ms |
| `MS` 自律送信周期 | **1000 ms** | `TIMER_UART_OUTPUT` (プローブ `IM_110.h:87`) |
| 本体 `HAL_UART_Transmit` タイムアウト | 100 ms | `IM-110/Core/Src/IM_110.c:169`（送信側ブロック時間） |
| プローブ起動完了待ち | 暗黙（電源立ち上がり数十 ms） | 本体は PROBE 電源供給後すぐに `MS\r\n` を送る。明示的な待機は無し |

### 4.2 コマンド応答タイムアウト（本体側）

本体がコマンドを送信してから、プローブ応答行（`OK` / `NG` / 値応答 / 複数行の先頭）を 1 行以上受信するまでの上限。**コマンド種別により 2 値**:

| 区分 | タイムアウト値 | 対象コマンド |
|---|---|---|
| **fast** | **500 ms** | `VR`, `SP`, `SEL`, `SS`, `MS`, `MD`, `MDR`, `SID`, `SADZ`, `SADS`, `SADA`, `SADC`, `RPI`, `RPG,<N>`（単一ページ）, `WPG` |
| **slow** | **3000 ms** | `RPP`（23 行ダンプ、約 720 ms 伝送 + 処理）、`WPP`（Flash 書込 100-500 ms を含む）、`RPF`（統合ストア 512B の 2KB ページ消去/書込を含む）、`RPG`（18 行ダンプ 約 1.1KB 伝送）、`WSC`（統合ストア flash 書込を含む） |

- FW 側で `#define CMD_TIMEOUT_FAST_MS 500` / `#define CMD_TIMEOUT_SLOW_MS 3000` 等として定数化する
- コマンド発行時、ディスパッチャは区分を参照して待機タイムアウトを選ぶ
- `RPP` / `WPP` 以外の新コマンドを追加する場合はデフォルト fast とみなし、実測で slow が必要な場合のみ分類を見直す
- MS 自律送信中のコマンド応答は測定値行と混在する。本体パーサは §3.3 の規則（行頭が数字 or `-` なら測定値、非数字なら応答）で分岐する

### 4.3 タイムアウト時のリトライ

**コマンド応答タイムアウト → 原則 1 回リトライ**。ただし以下のコマンドはリトライしない（副作用回避のため）:

| コマンド | 除外理由 |
|---|---|
| `SADS,N` | 空中の生 mV を span 基準として記録する（MLSS AD0）。時間経過で AD 値がドリフトするため、リトライ時の校正結果が 1 回目と異なる値になる |
| `SADZ,N` | 同上（残置・計算未使用だが `ADC_Zero` を上書きするため副作用あり） |
| `MS` (引数省略形) | プローブ実装がトグル式 (`MS_flag ^= 1`) のため、2 回実行すると元の状態に戻る (OFF→ON→OFF)。ただし新規本体コードは **`MS,1` / `MS,0` の明示指定を使う**（冪等、§3.3 推奨）ためリトライ可能 |

リトライしないケースでタイムアウトが起きた場合は即座に失敗扱い。UI には積極的エラー表示せず、ログのみ記録（§5.5 参照）。

**MS 自律送信（測定値行）の受信タイムアウト → リトライしない**:

- 上限は **2000 ms**（自律送信周期 1000 ms の 2 倍、ジッタ吸収のため）
- 該当測定値の UI 表示を `----` に切り替える
- 次の有効測定値行が届いたら自動で通常表示に復帰
- 連続的に測定値タイムアウトが続く場合は §5.4 の切断判定に移行する（具体ロジックは §9 TODO）

## 5. エラー処理

### 5.1 プローブ側の応答エラー (`NG\r\n`)

以下のケースでプローブは `NG\r\n` を返す:

| 発生条件 | 対象コマンド | 判定箇所 |
|---|---|---|
| パラメータ欠落（カンマの後に値が無い） | `SP`, `SEL`, `SS`, `SID`, `SADZ`, `SADS`, `SADA`, `SADC` | 各コマンドの `strtok` 後 NULL チェック |
| パラメータ形式不正（`strtof`/`strtol`/`strtoul` の失敗） | 同上 | `endptr` チェック |
| パラメータ範囲外 | `SP` (duty 0.0〜1.0 / idx 0〜4)、`SEL` (0〜2)、`SS` (0〜1)、`SADZ`/`SADS` (0〜4)、`SADA` (0〜255) | 各レンジ比較 |
| `SADC` の書式不正 | 4 文字の `'0'`/`'1'` 以外を含む | `IM_110.c:543-550` |
| 14 コマンドのどれにもマッチしない | 全未知コマンド | `IM_110.c:386` |

`NG\r\n` には理由コードが無いので、本体側は送信直前のコマンドと照合して原因を推定する。

**理由コード化しない方針** (v0.4.0 で確定): 本プロトコルは IM-110 本体⇔プローブの閉じた系であり、本体側の NG 発生時の挙動は §4.3 / §5.5 に従い「リトライ → 失敗なら `----` 表示 / ログ記録」で一律となる。理由（`RANGE` / `FORMAT` / `UNKNOWN` 等）が分かっても本体の分岐が変わらないため、理由コードを返す実装コストに対する価値が薄い。デバッグ用途も本体側で「送信したコマンド文字列 + NG 到来」のログから推定可能。将来、BLE 経由で外部診断治具を本格運用する等の要求が出てきたら再検討する。

### 5.2 CRC / チェックサム

- **RS-232C 通信では CRC/チェックサムを一切使用していない**。ノイズによる文字化けは検出できない。
- （参考）本体側 1-Wire EEPROM 通信 (`Wire.c`) には XOR チェックサムがあるが、これは RS-232C とは別系統。

### 5.3 HAL 層のエラー処理

**仕様**: 両側とも `HAL_UART_ErrorCallback()` を実装し、パリティ / フレーム / ノイズ / オーバーラン (PE/FE/NE/ORE) フラグをクリアした上で DMA 受信を再開する。上位層への通知は行わない（§5.5 の積極的エラー表示なしポリシーに準拠）。エラーカウンタは現時点では保持しない。

- **本体**: 実装済み (`IM-110/Core/Src/LinkSerial.c:200-212`)。PE/FE/NE/ORE フラグクリア後に DMA 受信を再開
- **プローブ**: **実装済み (Ver.0.17)**。`IM_110.c` の `HAL_UART_ErrorCallback()` で `USART2` のとき `HAL_UART_AbortReceive()` → PE/FE/NE/ORE フラグ浄化 → `clear_RecvData()` → `HAL_UART_Receive_DMA()` 再アームで RX を復旧する。**未実装だと ORE 一発で DMA 受信が停止したまま復旧せず、以後コマンド不検知→測定値ストリーム停止 (実機で MLSS=0 として顕在化) する**。特に統合ストア書込 (WSC の flash 消去/書込) 中の CPU ストールで ORE→RX 停止し、その後の `MS` を取りこぼす経路を救済する。本体 `LinkSerial.c:200-212` と同系ロジック。実装イメージ:

  ```c
  void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart) {
      if (huart->Instance != USART2) return;
      __HAL_UART_CLEAR_PEFLAG(huart);  // PE/FE/NE/ORE 一括クリア
      HAL_UART_Receive_DMA(huart, RecvData, sizeof(RecvData));
  }
  ```

プローブ側未実装による現実リスクは限定的（プローブが受ける最長コマンドは `SID,4294967295\r\n` = 15 バイト、受信バッファは 512 B でオーバーフロー余地は十分）だが、電源ノイズや信号品質劣化で FE / NE が発生した場合に DMA が停止したまま復旧しない懸念が残るので、次回改版で確実に入れる。

### 5.4 通信切断の判定

**方式: MS 自律送信の間隔監視（パッシブ監視）** — 定期 VR ヘルスチェック等のアクティブ監視は採らない。

**判定ロジック**:

1. 本体は MS 自律送信の測定値行が届くタイミングを監視する
2. 直前の測定値行から **2000 ms** 経過しても次の行が届かなければ「1 回タイムアウト」とカウント（§4.3 の MS 受信タイムアウト）
3. **連続 3 回タイムアウト（= 6 秒無応答）** で切断扱いに遷移する
4. 切断扱い中に測定値行が 1 行でも届いた時点で、自動的に接続扱いへ復帰する（リセット時復帰処理は不要）

**前提**:
- この方式は `MS` 自律送信が ON の状態を前提とする。本体起動シーケンス (§6) で `MS\r\n` を 1 回送るので通常運用では必ず ON
- `MS` OFF 状態（調整モード等、将来の運用で `MS` をトグル OFF する場合）では本方式は機能しない。将来 MS OFF 運用を導入する際は別途アクティブヘルスチェックの追加を検討する（§9 TODO）

**UI の扱い** (§5.5 と統一):
- 切断扱い中の数値表示は引き続き `----`（ロスト扱いと切断扱いで UI 差別化しない）
- 接続状態を明示するアイコン / インジケーターは **現時点では設けない**。将来の設定画面 / 通知 UI 追加時に再考する

**本体 FW 実装の想定**:
- MS 受信ハンドラで失敗カウンタをインクリメント、成功受信時に 0 リセット
- カウンタが 3 以上なら全測定値 UI を `----` 表示のまま据え置き、ログに「probe disconnected」を 1 回記録（切断遷移時のみ、連続で出さない）

### 5.5 UI / 運用ポリシー（タイムアウト時）

- **積極的なエラー表示はしない**: モーダルダイアログ / トースト / 画面上のエラーバナー等は出さない。ユーザー操作を邪魔する表示は避ける
- 失敗（コマンドリトライ後の失敗、測定値未到着、HAL エラー等）は **ログのみ** 記録する（デバッグ用、本番 UI には露出させない）
- MS 自律送信の測定値行が §4.3 に従い 2000 ms 届かない場合は、該当値の UI を `----` に置き換え、次の有効値で自動復帰
- 連続的なタイムアウトが発生した場合は §5.4 の通信切断判定に移行する（判定条件は §9 TODO で別途仕様化）

## 6. 起動シーケンス

### 6.1 現行 FW の実装 (本体 Ver.0.14 × プローブ Ver.0.11、ハンドシェイク無し)

```
[プローブ側]
1. 電源投入 (本体 CN4.1 → ケーブル → プローブ TP25 VIN)
2. STM32G070 起動 → HAL 初期化 → USART2 DMA 受信開始 (main.c:122 uart_init)
3. バナー送信: "IM-110 Probe Program Test\r\n" (main.c:123)
4. Flash パラメータ読込、MCP3424 / HSPPAD143 初期化
5. コマンド受信待ちループへ (`CheckSerialCMD` を LF 受信毎に呼ぶ)

[本体側]
A. 電源投入 → STM32L452 起動 → HAL 初期化
B. LPUART1 DMA 受信開始 (Probe_uart_init, IM_110.c:148-159)
C. プローブ電源供給 (本体→プローブ +5V 給電線、CN4.1)
D. 一定時間経過後、Probe_Request_MD() で "MS\r\n" 送信 (IM_110.c:218-224)
   — ここで `Probe_MS_started` フラグを立てる (1 回限り)
E. プローブから 1 秒周期で測定値が自動送信されるので、Probe_Process_MD() で解析
```

- プローブ起動バナー (`IM-110 Probe Program Test\r\n`) は本体パーサで数字/符号以外の行として無害に捨てられる (§3.3 の区別ルール)
- 疎通確認も Ver 照合も無し。ケーブル抜け等の異常を起動時に検出できない

### 6.2 仕様: 軽量ハンドシェイク (v0.4.0 で規定、本体 FW 実装待ち)

本体起動時に `VR` で疎通確認とログ記録を行う軽量ハンドシェイクを導入する。**Ver 照合は当面行わない**、失敗しても通常動作 (`MS\r\n` 送信) へ進む。将来 §7 の互換性ポリシー有効化や完全なハンドシェイクに段階的に拡張する余地を残す。

```
[本体側の新シーケンス]
A. 電源投入 → STM32L452 起動 → HAL 初期化
B. LPUART1 DMA 受信開始
C. プローブ電源供給
D. 200 ms 待機 (プローブ STM32G070 起動完了を待つ暗黙マージン)
E. "VR\r\n" 送信 → fast タイムアウト 500 ms 待機 (§4.2)
   - 応答が "IM-110 Probe Ver." で始まる → ログ "Probe connected: <応答文字列>"
   - タイムアウト → 1 回リトライ → 失敗ならログ "Probe not responding at startup"
   - 応答が異形式 → ログに原文記録
F. いずれの結果でも "MS,0\r\n" 送信 (冪等な保険、0.6.4 方式変更) → 通常動作へ
G. 本体が 500 ms 周期で "MD\r\n" を送信し、1 行応答を受信 (§3.3 ポーリング方式、0.6.4)
```

**方針のポイント**:
- **E で失敗しても G のポーリングは続ける**: プローブが後から物理接続 / 電源投入された場合でも、MD ポーリングの最初の応答で §5.4 の切断判定が復帰扱いに戻る（能動再試行は不要）
- **200 ms 待機の根拠**: プローブ側 HAL 初期化 + Flash 読込 + MCP3424 初期化で数十〜100 ms 程度かかると見積もり、マージンを含めて 200 ms。実機計測で調整の余地あり
- **ログ出力のみ、UI 表示はしない**: §5.5 の積極的エラー表示なしポリシーに統一

### 6.3 将来案: プローブ起動時の MS 自動開始

プローブ FW を次に改版するタイミングで、**起動時 `MS_flag = 1` 相当を内部でセット** する変更を入れる選択肢がある。

- 実装箇所: プローブ `main.c` の初期化ブロックで `MS_flag = 1` を既定値に
- メリット:
  - 本体は `MS` 送信を省略でき、§6.2 のハンドシェイクが純粋に「疎通ログ記録」のみに簡素化
  - 再接続時 (ケーブル抜き差し) も本体介在なしに自動送信が復旧
- デメリット:
  - 調整モードで MS を止めたい場合、明示的に `MS,0` 等で OFF する必要あり（現状実装はトグル式、§9 TODO の `MS` 引数仕様化と連動）
  - プローブ単独で生測定値を流し続けるため、想定外の受信先で問題になる可能性
- 判断: 採用するかはプローブ FW 改版時に決める（§9 TODO）

## 7. プロトコルバージョニング

このプロトコルは `MAJOR.MINOR.PATCH` で管理する。

- **MAJOR**: フレーム構造やコマンド体系の後方互換を破る変更
- **MINOR**: コマンドの追加（既存コマンドは不変）
- **PATCH**: ドキュメント整備、仕様明確化のみでバイナリ不変

### 7.1 互換ポリシー

本体とプローブの互換性判定ルール:

- MAJOR 一致必須
- 本体の MINOR ≥ プローブの MINOR （＝本体は古いプローブを許容する、逆は不可）
  ※ このポリシーはプロジェクトに合わせて書き換えてください

### 7.2 バージョン管理とリリース

- 本リポジトリ (IM-110-system) のこのドキュメント冒頭の `版` を更新する
- 本体側 (`IM-110`) のコードに `#define PROTOCOL_VERSION_*` を埋め込む
- プローブ側 (`IM-110_Probe`) のコードにも同じ定数を埋め込む
- 両側で `GET_VERSION` 経由で突合可能にする
